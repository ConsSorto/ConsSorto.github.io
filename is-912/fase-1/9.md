# 🏆 Clase 9: Evaluación Práctica (Sprint Review) y Cierre del Core

## 📖 Teoría: El Incremento del Producto y Autonomía Ágil

En metodologías ágiles, el cierre de nuestra Fase 1 equivale a una Sprint Review. El objetivo de un ingeniero de software no es solo escribir líneas de código, sino entregar un incremento de producto funcional y seguro. Ya construimos juntos los cimientos arquitectónicos, implementamos la Inversión de Dependencias (DIP) y aseguramos la creación de datos con DTOs.

Ahora, el equipo de desarrollo (ustedes) tomará el control para completar el Vertical Slicing de la entidad `HabitoGlobal`, finalizando el ciclo de vida de los datos en PostgreSQL.

## 💻 Laboratorio Práctico: El Reto del Arquitecto
Su misión es implementar los tres verbos HTTP faltantes para completar el estándar RESTful. No olviden que la petición debe atravesar la Capa API, validarse en la Capa de Aplicación y persistirse en la Capa de Infraestructura.

**Historias de Usuario a desarrollar:**
*   **Consultar por ID (`GET /api/habitos/{id}`):** El sistema debe permitir buscar un registro específico por su llave primaria.
*   **Actualizar (`PUT /api/habitos/{id}`):** El sistema debe permitir modificar el nombre de un hábito existente.
*   **Eliminar (`DELETE /api/habitos/{id}`):** El sistema debe permitir borrar físicamente un registro obsoleto de la base de datos.

## 📋 Criterios de Aceptación (Definition of Done)
Para que su código apruebe esta revisión, debe cumplir estrictamente con los siguientes estándares de calidad:

- [ ] **Contratos:** Ampliar la interfaz `IHabitoRepository` con los métodos `GetByIdAsync`, `UpdateAsync` y `DeleteAsync`.
- [ ] **Persistencia:** Implementar las consultas en `HabitoRepository` utilizando Entity Framework Core (ej. `_context.HabitosGlobales.FindAsync(id)`).
- [ ] **Defensa Perimetral:** Crear un nuevo contrato `UpdateHabitoRequestDto` para proteger la entrada de datos en el método `PUT`.
- [ ] **Reglas de Negocio:** Escribir un validador nuevo con FluentValidation exclusivo para la actualización.
- [ ] **Semántica HTTP:** Retornar `404 Not Found` si el ID solicitado no existe en la base de datos.
- [ ] **Operaciones Exitosas:** Retornar `200 OK` al consultar exitosamente, y `204 No Content` al finalizar un `Update` o `Delete`.
- [ ] **Documentación Viva:** Agregar los tres nuevos bloques de prueba en su archivo `HabitForge.API.http` y validar que funcionen antes de dar por terminada la tarea.
