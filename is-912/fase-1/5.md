# 🧩 Clase 5: Casos de Uso, Patrón Repositorio y Encapsulamiento de Inyecciones

## 📖 Teoría: Responsabilidad de Capas y Métodos de Extensión

Como ingenieros de software, sabemos que un sistema escalable debe mantenerse limpio. Si registramos todas nuestras dependencias (bases de datos, repositorios, servicios) directamente en el archivo `Program.cs` de la API, este se convertirá en un archivo gigantesco e inmanejable.

Para evitarlo, usaremos el **Patrón de Métodos de Extensión**. Cada capa de nuestra Clean Architecture tendrá un archivo estático llamado `DependencyInjection.cs`. La capa de Infraestructura será la única responsable de saber cómo inyectar a Entity Framework y sus repositorios, ocultando esa complejidad de la API.

### Análisis Estructural (Encapsulamiento)
*   **Aplicación**: Define el contrato `IHabitoRepository`.
*   **Infraestructura**: Implementa `HabitoRepository`. Crea un método de extensión para auto-registrarse en el contenedor de dependencias de .NET.
*   **API (Program.cs)**: Solo llama a un método limpio `builder.Services.AddInfrastructure()`.

## 💻 Desarrollo Práctico:

Vamos a codificar esta separación de responsabilidades paso a paso.

**1. El Contrato en la Capa de Aplicación (`backend/HabitForge.Application/Interfaces/IHabitoRepository.cs`):**

```csharp
using HabitForge.Domain.Entities;

namespace HabitForge.Application.Interfaces;

public interface IHabitoRepository {
    Task<IEnumerable<HabitoGlobal>> GetAllAsync();
}
```

**2. La Implementación en la Capa de Infraestructura (`backend/HabitForge.Infrastructure/Repositories/HabitoRepository.cs`):**

```csharp
using Microsoft.EntityFrameworkCore;
using HabitForge.Application.Interfaces;
using HabitForge.Domain.Entities;
using HabitForge.Infrastructure.Data;

namespace HabitForge.Infrastructure.Repositories;

public class HabitoRepository : IHabitoRepository {
    private readonly HabitForgeDbContext _context;
    
    public HabitoRepository(HabitForgeDbContext context) {
        _context = context;
    }

    public async Task<IEnumerable<HabitoGlobal>> GetAllAsync() {
        return await _context.HabitosGlobales.ToListAsync();
    }
}
```

**3. Encapsulando la Inyección (`backend/HabitForge.Infrastructure/DependencyInjection.cs`):**
¡Aquí ocurre la magia! Creamos una clase estática que concentra toda la configuración de esta capa.

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;
using HabitForge.Application.Interfaces;
using HabitForge.Infrastructure.Data;
using HabitForge.Infrastructure.Repositories;

namespace HabitForge.Infrastructure;

public static class DependencyInjection {
    public static IServiceCollection AddInfrastructure(this IServiceCollection services, string connectionString) {
        
        // 1. Inyectar la Base de Datos
        services.AddDbContext<HabitForgeDbContext>(options =>
            options.UseNpgsql(connectionString));

        // 2. Inyectar los Repositorios (La 'D' de SOLID)
        services.AddScoped<IHabitoRepository, HabitoRepository>();

        return services;
    }
}
```

**4. Un Program.cs Limpio y Elegante (`backend/HabitForge.API/Program.cs`):**
Nuestra API ya no necesita saber qué clases internas existen en Infraestructura. Solo pasa la cadena de conexión y delega el trabajo.

```csharp
using DotNetEnv;
using HabitForge.Infrastructure; // Importamos el método de extensión

var builder = WebApplication.CreateBuilder(args);

// Cargar variables de entorno locales
Env.Load();

// 1. Recuperar la cadena de conexión
var connectionString = Environment.GetEnvironmentVariable("ConnectionStrings__PostgresConnection") 
                       ?? throw new InvalidOperationException("Falta la cadena de conexión.");

// 2. Registrar toda la infraestructura con una sola línea
builder.Services.AddInfrastructure(connectionString);

builder.Services.AddControllers();
var app = builder.Build();

app.MapControllers();
app.Run();
```
